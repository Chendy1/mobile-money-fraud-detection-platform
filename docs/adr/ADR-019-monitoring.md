# ADR-019: Monitoring with API metrics, Prometheus and Grafana, and checks on stored predictions
**Context.** The system now serves and streams predictions. Nothing yet says whether the service is up and fast, whether it is receiving sensible traffic, or whether its decisions look like they did when the model was accepted. Two different questions need two different tools: operational health (is the service working, how fast, how many errors) changes second by second and suits a time-series database; decision health (are the stored predictions consistent, complete and like a reference) is a batch question over the prediction store. Drift in the inputs is Phase 15 and model performance needs labels (up to 45 days late), so neither is attempted here.
**Decision.**
- The API exposes `GET /metrics` in Prometheus text format, with its own registry per app. Counters: requests by route template, method and status; transactions scored by action (first time only); repeated ids. Histograms: request time by route; the calibrated probability. Gauges, read at scrape time: model loaded, customers, transactions in memory, feature version. Label values are bounded on purpose: the route template (not the URL), `unmatched` for anything else, and a fixed list of methods; nothing carries a transaction id, customer id, amount or county. Scraping itself is not counted. The middleware is the outermost one, so refused (413) and failed (500) requests are counted too.
- Prometheus and Grafana are opt-in Compose services (`--profile monitoring`), pinned to image tags, published on 127.0.0.1 only, read-only root, capabilities dropped, limits set. Grafana has no default password (the container refuses to start without `GRAFANA_ADMIN_PASSWORD`), no sign-up and no anonymous access. Its datasource and a ten-panel dashboard are provisioned from files. Seven alert rules (server errors, invalid-request share, scoring time, flagged share high or zero, API down or not ready) are evaluated by Prometheus. There is no Alertmanager, so an alert is visible but delivered to no one.
- `python -m mmrisk.monitoring report` checks a prediction store: integrity (unique ids, probabilities in [0, 1], action and risk level agree, no missing times, reasons readable and absent for allowed transactions, one feature version), completeness (no empty windows, freshness against `--as-of`), review load against a capacity the user gives, and, with a baseline, flagged share, blocked share, volume per hour and the most unusual window. `baseline` freezes the statistics of a store believed healthy. Results are PASS, WARN, FAIL or skipped (with the reason); the exit code is 1 only for FAIL. The report is written as Markdown and JSON.
- All thresholds are assumptions in `mmrisk/monitoring/config.py`, and the alert thresholds are assumptions in `alerts.yml`.
**What was measured, and what it changed.** Fraud arrives in clusters (the same customers are flagged together), so a binomial z score overstates how unusual a window is. Comparing two healthy, independent weeks of the default synthetic data, the largest |z| of a daily window was 2.8 and of a 6-hour window 4.1. A single window therefore only warns, and only from |z| 5; the overall shares use the usual 3 (warn) and 5 (fail). This is from one dataset; real traffic would need its own calibration.
**Alternatives.** The Python client's default global registry (shared state between apps and tests); counting in the service itself (couples bookkeeping to the HTTP layer); logging structured events and deriving metrics (more to run); Evidently for these checks (Phase 15 chose its own PSI instead, ADR-020); comparing a window with the rest of the same store (that hides a problem that is present for the whole store); a hard-coded expected flagged share (invented; the baseline is measured instead).
**Consequences.** Checked without Docker: the Prometheus and Grafana files parse, every metric and label in an alert or a dashboard query exists in the API (the list of names is generated from the code), every query parses as PromQL (with the `promql-parser` package; `promtool` was not available), the compose services are locked down, and the Grafana start-up guard works in a real shell. Not verified: pulling the images, Prometheus loading the rules, Grafana provisioning and rendering the dashboard, and the read-only Grafana container (it may need another writable path). Limits: the checks see decisions, not correctness or input drift; the baseline must come from a store someone judged healthy; the service keeps its counters in memory, so a restart resets them (Prometheus handles resets in `rate` and `increase`); `/metrics` has no authentication, like the rest of the API (Phase 18).
