# ADR-018: A streaming simulation with a bounded in-process queue, a reorder buffer and an append-only prediction store
**Context.** The platform scores single transactions (Phase 11) but nothing yet behaves like a live feed. Later phases need one: monitoring needs traffic (Phase 14), drift detection needs predictions over time (Phase 15), the dashboard needs something to show (Phase 17), and load testing needs a source of events (Phase 19). A real stream has problems the batch path never sees: events arrive late and out of order, are delivered twice, are sometimes corrupt, and a slow consumer must not make memory grow. Kafka was rejected for the project; the question is what to build instead that still exercises those problems honestly.
**Decision.**
- Replay stored transactions as events. `python -m mmrisk.streaming run` takes the lake, replays the history before a start time into the scoring service, and streams everything from the start time on. The start is `--from`, or `--last-days` (default 7) before the newest transaction.
- Delivery faults are injected from one seed, so a run is reproducible: random delay up to `--jitter-seconds` (which reorders arrivals), repeats (`--duplicate-rate`, a retry that arrives later), and corrupted copies (`--bad-rate`, amount 0, id suffixed `-BAD`, which must be rejected). With all rates at zero the stream is the input in order.
- Plumbing: a producer thread, a bounded `queue.Queue` and one consumer. A full queue blocks the producer (backpressure) and the time it waited is reported with the peak queue depth. There is one consumer on purpose: the scoring service needs each customer's transactions in time order and takes a lock anyway.
- A reorder buffer between the queue and the scorer does what a stream processor's watermark does. It holds events until none older can still arrive (newest event time seen minus `--max-lateness`), then releases them in (event time, id) order, the same order the batch path uses. An event that arrives after something newer was released is dropped as too late (a real system would use a dead-letter queue); an id seen before is dropped as a repeat. If the delay is at most the allowed lateness nothing is ever late; the tests prove the released order is always sorted whatever arrives.
- Scoring is in this process (`LocalScorer`, which validates exactly as the API does) or over HTTP against a running API (`HttpScorer`, standard library only, `--url`). Both return the same outcome names (scored, duplicate, invalid, unknown_customer, out_of_order, conflict, unavailable, error), and a test checks that they agree on every one. In HTTP mode `--from` is required and the API must have replayed exactly the history before it (`serve --history-until` the same time, or `MMRISK_HISTORY_UNTIL`), and must not have seen the stream.
- Every event ends in exactly one place: scored, rejected with a reason, or dropped by the buffer. The report states whether the books balance, and the command exits 1 if they do not, if the service was unavailable or errored, or if nothing was scored. The run gives up after 20 consecutive unavailable answers and stops cleanly if the scorer or the source fails (no thread is left waiting).
- Predictions go to an append-only store of Parquet part files (`data/predictions/part-NNNNNN.parquet`), each written under a temporary name and renamed, never rewritten, numbering continued across runs. Only first-time scores are stored. The run refuses a store that already has predictions unless `--append`, so two replays of the same events are not mixed by accident. A JSON run report is written beside it.
- `--speed` paces the stream (simulated seconds per real second; 0 means as fast as possible).
- Docker Compose gets an optional `simulator` service (profile `simulate`) that streams into the `api` service; `STREAM_FROM` sets both the stream start and the API's replayed history.
**Alternatives.** Kafka or Redpanda (rejected for the project: operational weight for one process); `asyncio` (no benefit with one consumer and a blocking scorer); letting the service reject late events (it does, but then late data is simply lost with no window to absorb ordinary jitter); storing predictions in a database (one more service; Parquet is what the later phases read); storing feature values in the prediction store (they can be recomputed from the lake by transaction id for replayed events).
**Consequences.** Measured in the sandbox on 4,698 transactions of the default dataset: 206 scored per second in process and about 123 per second over HTTP with faults on, with a median scorer latency of 4 to 8 ms and the queue full (backpressure working); these are one-process figures from a sandbox, not a benchmark, and the load test is Phase 19. Limits: the reorder buffer holds every event inside the lateness window, so its size grows with rate times lateness (the report gives the peak); lateness is event-time based and the stream's clock is the data's clock; faults are simple (no bursts, no dropped events, no clock skew); late events are counted, not kept; the service's history is in memory, so after a stream the API must be restarted before the same events are sent again; the stream carries no labels, so performance monitoring on streamed data waits for Phase 14 and later. The compose `simulator` service is **TO VERIFY** (the assistant cannot build images).
