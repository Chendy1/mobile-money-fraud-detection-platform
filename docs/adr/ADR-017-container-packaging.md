# ADR-017: Package the scoring API as one hardened container, run by Docker Compose on loopback only
**Context.** Phase 11 gave a service that runs from a Python environment. Phase 12 makes it run the same way on any machine with Docker, without installing the project, and gives later phases (event simulator, monitoring, dashboard) a compose file to extend. The development machine has 8 GB of RAM shared with Docker Desktop and WSL2, so the setup must be small. The API has no authentication or TLS yet.
**Decision.**
- One service for now: `api`. Training, the pipeline and MLflow stay on the host, because a container for them would compete for the laptop's memory and add nothing a person needs to see. Later phases add services to the same compose file.
- The image is a two-stage build on `python:3.12-slim-bookworm`. It installs only the `serve` extra (scikit-learn, LightGBM, FastAPI, uvicorn plus the base dependencies), not pytest, matplotlib, SHAP, MLflow or DuckDB. It adds `libgomp1` because LightGBM links the OpenMP runtime. It runs as the numeric user 10001. The model and the data lake are not in the image: compose mounts `models/advanced` and `data/processed` read-only. A model baked into an image would tie data and weights to a build, and would put anything in the lake into a layer.
- The build context is restricted by `.dockerignore` (data, models, MLflow files, `.git`, `.env*` except the example, key files).
- The port is published as `127.0.0.1:8000:8000`. Inside the container the server must listen on `0.0.0.0` (the container's own interface), so the command passes `--allow-external`, the flag the API otherwise requires; the host-side binding to the loopback address is what keeps the service local. Both facts are written beside the settings and checked by tests.
- Hardening: read-only root filesystem with a tmpfs `/tmp`, all Linux capabilities dropped, `no-new-privileges`, a memory limit, a CPU limit and a process limit. The memory limit comes from a measurement: about 290 MB with no history and about 530 MB peak with 200,000 transactions replayed (about 1.2 KB per transaction), measured on the sandbox without Docker, so 1 GB leaves room for roughly twice that history.
- The health check uses only the standard library (`urlopen` on `/ready`), so it costs almost no memory every 30 seconds, and it has a 120-second start period because the history is replayed before the service is ready.
- `python -m mmrisk.api smoke` checks a running service from outside with requests that cannot change its state: the health and readiness endpoints, the model description, an invalid body (422, input not echoed) and a customer that does not exist (404).
- A CI job builds the image and checks that LightGBM imports, that the user is 10001 and that the compose file is valid. It does not push anything.
- Tests check the Dockerfile and compose file without Docker: pinned tags, a non-root user, loopback publishing, read-only mounts, dropped capabilities, resource limits, no secrets, no extras beyond `serve`, a command that the real argument parser accepts, mounts that match what the command reads, and a build context that leaves data, models and secrets out. Mutations of each file make a specific test fail.
**Alternatives.** A model baked into the image (see above); a distroless base (no shell, harder to debug, and the OpenMP library still has to be supplied); running training in Docker (memory); Kubernetes (rejected for the project); a single `docker run` line (no declared limits or mounts to review).
**Consequences.** Not done, on purpose or for lack of access: the base image is pinned to a tag, not a digest (resolving a digest needs registry access, TO VERIFY); no vulnerability scan, SBOM or image signing (Phase 18); no TLS or authentication (Phase 18); no registry push; one architecture. The image build, the container run with a read-only filesystem and the compose startup have not been run by the assistant, whose sandbox cannot reach Docker Hub: they are **TO VERIFY** on the author's machine. What was checked natively: a clean environment holding only the `serve` dependencies passes `check`, `serve` and `smoke`; LightGBM links `libgomp`; `docker compose config` accepts the compose file. Limits: memory grows with the replayed history; Windows bind mounts reach the lake through WSL2, which may slow the start; the model is a pickle, so a read-only mount does not make an untrusted file safe.
