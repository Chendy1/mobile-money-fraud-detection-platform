# ADR-021: Gated retraining with a file-based model registry
**Context.** Phase 15 can say that inputs moved; it cannot say that a new model is better. A retrain that replaces the model on a schedule, or on an alarm, without checking the result, turns a data problem into an outage. Phase 10 left "registry and gates" for this phase.
**Decision.**
- Registry: a folder (`models/registry`), no server. `versions/vNNNN/` holds the same two files the API already loads plus `version.json` (stage, parent, SHA-256 of the model file, metrics, every gate result). `production.json` names the serving version and is replaced atomically; `history.jsonl` is appended to and never edited (register, stage change, promote, rollback, with the reason and whether it was forced). A version's stage is `candidate`, `approved` or `rejected`. `--model-dir <registry root>` works everywhere a model folder did (API, drift, monitoring) because `load_model` follows `production.json`. A running API keeps the model it loaded; restart it after a promote or a rollback.
- Trigger (`retrain check`, exit 1 when a retrain is recommended): the latest drift report says major drift; the champion's data ended more than 90 days before the end of the lake (simulated time, not the clock); at least 200 fraud labels exist on transactions newer than the champion's data; or `--force`. The age and label triggers exist because the accumulating features (`n_prior_txns`, `account_age_days`) are deliberately not counted by the drift report (ADR-020): a model can age without any PSI alarm. An input that is missing is shown as `unknown`, never as "no".
- Candidate (`retrain run`): the same split as the advanced step, anchored at the end of the lake, the same LightGBM tuning on validation, Platt calibration on validation, and the champion's (assumed) cost model, so the comparison is about the scores. Both models are scored once on the newest matured 45-day window, the champion with its own calibrator as it is deployed. The candidate is always registered, rejected ones included, so a failure can be examined.
- Gates (required unless marked): enough fraud in train, validation and test (stops before training); the champion did not train into the test window (otherwise it is graded on its own homework); PR-AUC and realised cost per 10,000 not worse than the champion by more than a margin, judged on a customer-level bootstrap of the paired difference; calibration error not worse by more than 0.005; the share of REVIEW and BLOCK within 0.5 to 2 times the champion's; the saved candidate reloads and reproduces the in-memory probabilities (this also checks its feature version). Agreement on actions (at least 70%) is advisory and never blocks, because a better model may legitimately disagree.
- Promotion is a separate step: `registry promote vNNNN --reason "..."` (refused unless approved, and refused for a quick-mode candidate; `--force` is recorded). `--auto-promote` is opt-in, needs every required gate, and never applies to a quick-mode candidate. `registry rollback --reason` switches back to the version it replaced.
**Measured** (sandbox, default dataset of 200,000 transactions, champion = the advanced model, candidate trained on the same data and window with a fresh tuning run; about one minute). Same data end, so this shows the machinery and the noise, not that a retrain helps: PR-AUC 0.498 vs 0.502, difference interval [-0.020, +0.028]; cost per 10,000 KES 39,289 vs 37,935, difference interval [-3,700, +1,083]; ECE 0.0019 vs 0.0015; share of REVIEW and BLOCK 2.72% vs 2.82%; the two agree on 98.6% of actions. With a PR-AUC margin of 0.01 and a cost margin of 2% the candidate was REJECTED, although no worse: the test window holds about a hundred frauds and the intervals are wider than those margins. The margins were then set to 0.03 and 5%, after seeing that comparison, which is a weakness of these numbers.
**Alternatives.** MLflow Model Registry (the local tracker is sqlite and its registry would add a second source of truth next to `production.json`; a registry folder is readable and testable); a champion-challenger shadow period on live traffic (needs traffic, and the label delay is 45 days); promoting on a better point estimate alone (noise of this size would swap models at random); a schedule without gates.
**Consequences.** Limits: every threshold is assumed and none was calibrated against real losses; with a window of this size the gates cannot tell models apart by less than about 0.03 PR-AUC, so a real improvement smaller than that will not be recognised and a regression smaller than that will not be caught; the checksum detects corruption, not an attacker who can write the registry (the model file is a pickle, so only use a registry you created); there is no locking, one writer at a time; the history is a file, not an audit system; the cost model carried over from the champion is assumed; the label delay means a candidate is always judged on data at least 45 days old; no shadow or canary stage exists.
