# ADR-016: A local scoring API with a framework-free core, strict input rules and in-memory history
**Context.** The trained `RiskModel` (Phase 8) and the online feature path (Phase 6) exist but nothing serves them. The API must give exactly the answer the batch path gives, must be safe to run on a laptop, and must not pretend to be more than it is: one process, no authentication, synthetic data.
**Decision.**
- Two layers. `mmrisk.api.service.ScoringService` has no web dependency: it holds one `RiskModel` and one `OnlineFeatureState`, and `mmrisk.api.app` is a thin FastAPI wrapper. The core is testable without HTTP and reusable by the event simulator in Phase 13.
- `POST /v1/score` takes one transaction (the ten input columns), computes its features from the history seen so far with the same code as the batch path, assesses it, and only then records it. A failure before the last step leaves the history unchanged. The response has the calibrated probability, the action (ALLOW, REVIEW, BLOCK), the risk level, the expected cost of each action (labelled assumed), reason codes when the action is not ALLOW, and the feature version.
- Idempotency: the same `transaction_id` with the same content returns the first answer (`duplicate: true`) and is recorded once; the same id with other content is a 409. Answers are cached for the last 10,000 ids only; an id older than that that is sent again is treated as a new, out-of-order transaction (409).
- An older transaction for a customer (not later than the last one in the history) is a 409 and an unknown customer is a 404. History must therefore arrive in time order per customer, as the feature code requires.
- Input is validated strictly: unknown fields refused, allowed values and the amount limit taken from the ingestion rules, the counterparty must fit the transaction type, integer amounts only (no strings or floats), local East Africa Time without a timezone, identifiers limited to `[A-Za-z0-9_-]{1,64}`. Error responses give field names and messages, never the submitted values. Bodies over 8 KB get a 413, whether or not a length is declared. Unexpected errors return a generic 500 and are logged with a request id; the transaction body is never logged.
- Local only. The service listens on 127.0.0.1 and refuses another address unless `--allow-external` is given (with a warning). There is no authentication or TLS; both belong to Phase 18. `/docs` can be switched off.
- Startup refuses a model built for another feature version. The model bundle is a pickle (joblib): only files this project wrote should be loaded, and the docs say so.
- History at startup is replayed from the cleaned layer (all of it, or before `--history-until`). `python -m mmrisk.api check` streams the last N transactions through the service and compares them with batch scoring, and reports the latency measured on that machine.
- No batch endpoint and no metrics endpoint yet (monitoring is Phase 14); `/health` is liveness and `/ready` is readiness.
**Alternatives.** Putting the logic in the route functions (hard to test, hard to reuse); a feature store or Redis for history (extra services, rejected at this scale, Feast is out of scope); a Kafka consumer (rejected); accepting extra fields and coercing types (hides client bugs); returning full SHAP vectors (large and easy to misread; reason codes are enough).
**Consequences.** On the sandbox's default dataset (5,000 customers, 200,000 transactions) the service matched batch scoring to 0.0 in probability and action for 300 held-out transactions, with a median of 4.5 ms and p95 of 7.3 ms per transaction on one process. Limits: state is in memory and lost on restart (replay rebuilds it); one process and one lock, so throughput is one transaction at a time; each score recomputes over that customer's whole history, so latency grows with history length (a bounded-aggregate store is the production answer); a replayed history that contains transactions later than the ones being scored will make them 409; costs and thresholds are assumptions; the reason codes describe the model, not the cause. Load behaviour is measured in Phase 19.
