# ADR-008: Layered ingestion with immutable raw, quarantine and a ledger
**Context.** Bad, duplicated and replayed data is normal in real pipelines. We need to ingest repeatedly without creating duplicates, survive crashes mid-write, and always be able to explain where a row came from.
**Decision.**
- Layers: `raw` (verbatim copy of each source file, immutable), `validated` (rows that passed structural gates), `quarantine` (rejected or conflicting rows with a reason and the original row as JSON), `cleaned` (deduplicated, standardised, partitioned by date).
- Idempotency: a batch is `(table, SHA-256 of the file)`. A ledger records COMPLETE batches; readers only see COMPLETE batches; the ledger is written last, and every file is written atomically (temp file then rename).
- Duplicates: first write wins. An identical later copy is dropped and counted; a later copy with different content is quarantined as a conflict. Nothing is dropped silently, and row counts must add up (`rows_in = rejected + duplicate + conflict + cleaned`), which `reconcile` checks.
- Partitioning: Hive-style daily `event_date` for transactions and `label_available_date` for labels. Dimensions are full snapshots; the latest completed snapshot is the cleaned dimension.
- Scope: Phase 3 enforces only structural gates (readable, schema match, castable, required fields present). Domain quality rules arrive in Phase 4 on the same quarantine mechanism.
**Alternatives.** Overwrite-in-place loads (not idempotent, no audit trail); an database upsert (heavier; hides lineage); last-write-wins dedup (silently rewrites financial facts); monthly partitions (fewer small files, but coarser incremental loads).
**Consequences.** Safe re-runs, recoverable crashes and full lineage, at the cost of extra storage (about 3 copies of the data) and many small files (about 16 KB per daily partition on the default dataset). Compaction would be needed at larger scale. Label revisions (a later label for the same transaction) are treated as conflicts, not updates; revisiting that is future work. Reading the full cleaned layer to deduplicate does not scale beyond a few million rows without partition pruning or DuckDB.
