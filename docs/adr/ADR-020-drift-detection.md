# ADR-020: Drift detection with population stability index, against a frozen reference
**Context.** Phase 14 checks what the system decided. Phase 15 asks whether the data the model sees has moved away from what it was validated on. The model can degrade without any error: inputs shift, scores shift, decisions follow. Labels arrive up to 45 days late, so drift in the inputs and the scores is the earliest signal there is. It is also the trigger the gated retraining phase will need.
**Decision.**
- Reference: the model's validation window (read from the saved split: after `val_start`, up to `test_start`), summarised to a few numbers per feature (bins and shares; no rows) and for the model's own score. Validation is out of sample for the scorer and is the window the calibration was fitted on. `--from` and `--to` choose another window.
- Statistic: population stability index, `sum((cur - ref) * ln(cur / ref))` over bins. Numeric features use ten quantile bins whose cut points are observed reference values (interpolated cut points made an empty bin when many values tie, which was a measured bug). Features with at most 12 distinct values, booleans and categories use one bin per value. A value the reference never saw has a bin of its own, and so do missing values (a missing value here means "no history yet", which is information). Shares are floored at 0.0001. The noise level, `(bins - 1)(1/n_ref + 1/n_cur)`, is printed next to every PSI: it is what two samples of the same distribution show.
- Thresholds: 0.1 moderate, 0.25 major (conventions from credit scoring; assumed). `drift_detected` is true when the score or any counted feature is major. Fewer than 500 current rows scores nothing, and a run where nothing could be scored is an error, not "no drift".
- Two kinds of feature move for reasons that are not a change in the world, found by measurement:
  - Calendar: `is_salary_window` (days 25 to 3) and `day_of_week`. A week has the wrong mix of salary days, and a day has one weekday. They are not scored for a window shorter than their cycle (31 and 7 days); when scored, they count.
  - Accumulating: `n_prior_txns` and `account_age_days` grow as time passes. They are scored and shown but do not by themselves declare drift. Their PSI against the time since the reference is in the table below, so a feature moving faster than the calendar would be seen.
- Output: `report.md` and `report.json` (with `drift_detected`, per-feature PSI, and a per-day series so a sudden change differs from a slow one), exit code 1 on drift, 2 on a mistake. `--scale-amounts` multiplies the amounts in the current window to demonstrate detection; it never touches the lake.
- The current window is a time window of the lake, scored in batch (batch and streaming scoring are proven equal in Phase 13), not the prediction store: the store keeps inputs and outputs but not the 28 features.
**Measured** (default synthetic dataset, 200,000 transactions, reference = the 25,451 validation transactions, 7-day windows after it; sandbox):

| Weeks after the reference | Largest PSI of any counted feature | Score PSI | `n_prior_txns` | `account_age_days` |
|---|---:|---:|---:|---:|
| 0 to 1 | 0.024 | 0.009 | 0.027 | 0.017 |
| 4 | 0.036 | 0.027 | 0.095 | 0.035 |
| 8 | 0.015 | 0.025 | 0.117 | 0.054 |
| 12 | 0.019 | 0.058 | 0.275 | 0.139 |

Over the 12 weekly windows after the reference no drift was flagged. Features that did not change sit at the noise level (0.001 to 0.01). The windows 22 to 27 weeks BEFORE the reference were flagged: early in the history customers have few prior transactions and `secs_since_last_inbound` moves from 0.25 to 0.98, which shows that the start of this dataset is not stationary. Injected multiplicative shifts of amounts in the last week: x1.3 PSI 0.04 (not flagged), x1.5 0.09 (not flagged), x2 0.23 (moderate), x3 0.56 (major, drift declared). The detector therefore sees large shifts, and a 50% rise in amounts goes unnoticed. A report run takes about 15 s and peaks near 420 MB (sandbox, 200,000 transactions).
**Why not Evidently.** The stack named it. Installing it into a clean environment added about 950 MB of packages (pandas, plotly, nltk, scipy and more) and pulled a second dataframe library into a project that uses Polars, on a machine with 8 GB of memory and limited disk. PSI is a small formula; it is tested against an independent calculation and hand-computed values, and the noise level is shown. Evidently could be added later as an optional extra for HTML reports.
**Alternatives.** Kolmogorov-Smirnov tests (with thousands of rows they reject for differences too small to matter); a rolling reference (a slow drift would never show, and the reference would drift with it); the training window as reference (the model was fitted on it; its score is too confident); comparing against the prediction store only (it does not hold the features).
**Consequences.** Limits: a reference from one validation window carries that window's own quirks; PSI looks at each feature alone, so a change in the relation between features, or between features and fraud, is invisible; the thresholds are conventions; features that accumulate will eventually exceed the limits and the report shows them but does not decide on them, so retraining on age needs its own rule (Phase 16); no windows of real traffic exist, so all measurements are from one synthetic dataset. Drift is not an error rate: no drift does not mean the model is right.
