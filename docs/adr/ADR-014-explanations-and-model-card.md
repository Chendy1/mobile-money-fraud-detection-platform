# ADR-014: Exact tree explanations, cross-checked three ways, and a model card generated from saved results
**Context.** A risk score that cannot be explained is hard to review, debug or defend. Explanations also mislead easily: a bar chart of "importance" looks like a statement about causes, different measures disagree, and a fraud rate of 0.4% means an average over all transactions describes ordinary behaviour, not fraud. The project also needs a model card that cannot drift away from the numbers.
**Decision.**
- Use LightGBM's own exact TreeSHAP contributions (`pred_contrib`) instead of an approximation. For every transaction, a base value plus one contribution per input adds up to the model's log-odds; the run reports the largest additivity error and a test fails above 1e-8. Contributions of one-hot and cyclic columns are summed back to the 28 catalogue features, and amount and its logarithm are judged as one unit. Because Platt calibration with the logit link is a straight line in log-odds, contributions multiplied by its slope add up to the calibrated log-odds, the scale used for reason codes.
- The `shap` library is an optional extra used only in a test that checks our values against it. It is not a runtime dependency.
- Report three views of importance side by side, never one: the average effect over all test transactions, the average effect over fraud-labelled transactions, and the PR-AUC lost when a feature (or a whole feature group) is shuffled. Agreement between them is computed and stated, including when it is low.
- Cross-check the explanations: stability between the validation and test windows (all rows and fraud rows), and a refit without each important feature, scored on the validation window only, over several seeds; a change smaller than twice the seed-to-seed spread is called noise. The test window is never used to make a choice, and nothing in this phase changes the shipped model.
- Reason codes: for a flagged transaction, the at most three features with the largest risk-raising effect, as a label and the transaction's own value, on the calibrated scale. Exposed as `RiskModel.explain(df)` for later serving. They describe the score, not intent or cause.
- Examples in the report are picked by fixed, stated rules (the highest-probability blocked fraud, the highest-probability blocked legitimate transaction, the largest allowed fraud), not for how they look.
- A descriptive table of who gets flagged, by segment, channel, away-from-home and account age, with intervals. It is a check for uneven treatment, not a fairness test.
- Optional audit against the hidden truth: whether the signals each fraud pattern is built on appear among the reasons. The mapping from pattern to signals is the author's reading of the data dictionary and is labelled as an assumption.
- The model card (`docs/model-card.md`) is generated by `python -m mmrisk.models card` from the three files the earlier steps saved, and refuses to be written if one is missing. Prose that is not a number (intended use, out of scope, limitations) is fixed text that has to stay true; every number is read from the files.
**Alternatives.** The `shap` library as the explainer (an extra dependency and an approximation path with no gain for trees); LIME (unstable, no additivity); a single importance bar chart (hides the disagreement that this data shows); a hand-written model card (drifts from the results).
**Consequences.** On this synthetic data the three measures disagree, and the report says why. `segment`, a customer attribute, has one of the largest average effects and removing it lowers validation PR-AUC, so reason codes that cite it need review before being shown to anyone; the card says so. Some features are used by the fitted model yet replaceable by others; importance is therefore described as a property of this fitted model and never as a ranking of causes. Limits: explanations describe one model on one validation and one test window with about a hundred fraud cases each; shuffling is sensitive to correlated features (group shuffling is reported next to it); the pattern-to-signal mapping is a judgement; the slice table uses synthetic segments and noisy labels. Drift of explanations over time is a monitoring topic for a later phase.
