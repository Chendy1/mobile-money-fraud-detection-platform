# ADR-011: One shared, strictly backward-looking feature library for training and serving
**Context.** Most fraud models that look good offline fail in production for two reasons: leakage (a feature quietly uses information from the future, or from the label) and training/serving skew (the batch pipeline and the online service compute "the same" feature differently). Both are hard to see in metrics and cheap to prevent by design.
**Decision.**
- Every feature is defined once, in `mmrisk.features.compute.compute_features`, in Polars. A row's features use only rows strictly before it in (timestamp, transaction_id) order. Time windows use a left-closed interval, so they exclude the row itself and any row with the same timestamp; the "last inbound transfer" lookup is an as-of join against one microsecond before the transaction (strictly earlier, and independent of the Polars version).
- The online path (`OnlineFeatureState`) builds a small frame from a customer's history plus the new transaction and calls the same function. There is no second implementation to drift. A test streams transactions through it and requires exact agreement with the batch result.
- Features take no labels and no statistics computed over the whole dataset. Labels are attached separately by `training_table(as_of)`, which keeps only rows whose label was available by `as_of` and never treats recent unlabelled transactions as legitimate. Features are identical whatever `as_of` is.
- Left out on purpose: raw identifiers (customer, device, counterparty), merchant/agent fraud-rate encodings (target encoding that leaks without strict time handling), and a global amount percentile (depends on future rows). The EDA used that percentile; the feature library does not.
- Windows are bounded (at most 30 days) apart from the lifetime counters, so a production store would need only bounded state.
- A leak audit (`python -m mmrisk.features audit`) reports each feature's single-feature AUC and flags any near 0 or 1.
**Alternatives.** A feature store such as Feast (a large dependency for one model and one machine; rejected in the plan); writing SQL for training and Python for serving (the usual source of skew); using DuckDB for features (it is an optional dependency here, and the library must run inside the API); precomputing features once and joining labels into the same file (makes it easy to leak label timing).
**Consequences.** Training and serving cannot disagree on a feature, and leakage is testable: truncation tests, a brute-force-style cross-check against the independent DuckDB definitions, and mutation checks that were seen to fail. Costs: the online path recomputes a small frame per request (fine here, not at scale); the online history is unbounded in memory; feature thresholds (30-day baseline, 2-hour cash-out window, 1-hour location jump) are illustrative and untuned; the inbound-transfer features exploit how the simulator creates mule cash-outs, so their strength is optimistic compared with real data; and this ADR does not make the labels themselves unbiased (see the EDA's ground-truth audit).
