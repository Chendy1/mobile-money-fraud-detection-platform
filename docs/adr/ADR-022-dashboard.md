# ADR-022: A read-only local dashboard on a tested data layer
**Context.** Phases 13 to 16 write files: predictions, monitoring and drift reports, a model registry, retraining results. A person who has to decide (review a transaction, judge a model, act on a drift alarm) should not have to open five folders. The stack named Streamlit.
**Decision.**
- Two layers. `mmrisk.dashboard.data` holds every number and table the pages show as plain functions on files; it imports no Streamlit and is tested directly. `mmrisk.dashboard.app` is a thin page that only lays those results out. A rule found while building it: whatever can be wrong lives in the first layer, where it can be tested without a browser.
- Read-only. The dashboard writes no file, calls no service and starts no process (a test searches the page source for file writes, HTTP clients and subprocesses). It reads the prediction store, the monitoring baseline, the drift report, the registry and the retraining results from their default paths, each overridable.
- Each source loads on its own. A loader returns "ok", "missing" (with the command that creates it) or "unreadable" (with the reason); one damaged file never takes the other pages down. The page for a missing store says to run the stream simulator.
- Pages: Overview (counts, flagged share, action mix, probability histogram, per-window volume and flagged share), Review queue (highest probability first, filters, one transaction with its reason codes), Health (the Phase 14 checks run on the current store, and the latest drift report; a drift report made with `--scale-amounts` is labelled a demonstration), Models (versions, production marker, the gate results saved with each version, recent registry history, the last retraining check).
- Freshness is judged against the newest event, not the clock, because the simulator replays old data. Without a baseline file the comparisons with a healthy period are skipped and the page says so.
- Safety. It binds to 127.0.0.1 and refuses another address without `--allow-external` (there is no login before Phase 18, and the page shows transaction details). Streamlit's usage statistics are switched off on the command line. Customer identifiers are masked by default (`C000123` becomes `C000***`); the person can untick the box. Text from the data (reason codes, identifiers) is shown through Streamlit's tables and JSON view, never as HTML; a test puts a `<script>` string in a reason code and checks it is carried as text.
- Packaging. `pip install -e ".[dashboard]"` adds `streamlit>=1.40`; it is not in the base, `api` or `serve` extras, so the scoring container does not grow. No container for the dashboard was built: Docker Hub is unreachable from the sandbox and Phase 20 covers the deployment. `python -m mmrisk.dashboard check` prints what each page would show without Streamlit, for troubleshooting.
**Measured** (sandbox, Linux, Python 3.13). Installing Streamlit 1.66.1 alone into a clean environment: 447 MB in 38 packages (pandas, pyarrow, altair, numpy among them), about half of what Evidently needed (ADR-020) but not small on a machine with limited disk. A prediction store of 8,173 events (14 simulated days): `dashboard check` takes about 1.8 s once files are cached by the operating system (the first run on a cold sandbox took 58 s, mostly importing the model libraries through the registry). Under Streamlit's test harness the first render took 8.2 s and a re-run with the cache 0.3 s. Page load time in a real browser was NOT measured. The visual layout was not looked at in a browser by the assistant (no browser session in the sandbox); it is checked only by the harness, so how it looks is TO VERIFY on your machine.
**Alternatives.** Grafana only (it shows the API's counters from Phase 14, not individual transactions, reason codes or the registry); a Streamlit page with the logic inline (untestable without a browser); a web framework with its own front end (more code than the question deserves); reading the API instead of files (the API does not keep history, and the files are the source of truth).
**Consequences.** Limits: the page reloads the whole store when a part file is added, so a store of millions of rows would need aggregation first (not built; about 8 thousand rows were tried); it shows nothing live unless Refresh is pressed or the page is reloaded; there is no login, no audit of who looked at what, and masking is a display convenience, not access control (anyone who can run it can untick the box and read the files); the review queue cannot record a decision (no label or case-management store exists); charts use Streamlit's defaults.
