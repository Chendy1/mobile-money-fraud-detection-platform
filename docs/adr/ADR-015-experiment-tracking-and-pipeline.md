# ADR-015: Local experiment tracking behind an interface, and one in-process training command
**Context.** Phases 7 to 9 each write their own reports and JSON files. Comparing two runs means opening files by hand, and nothing records which data or code produced a number. The project must stay free to run, work offline and never hold credentials.
**Decision.**
- One command, `python -m mmrisk.pipeline run`, runs features, baselines, the advanced model, explanations and the model card in one process. The features are computed once and shared. The stages are the existing functions, not a second implementation, so a pipeline run and the separate commands give the same numbers.
- Tracking sits behind a small `Tracker` interface. `MlflowTracker` writes to a local store (default `sqlite:///mlflow.db`); `NullTracker` keeps everything in memory (used by `--no-tracking` and by tests). MLflow is an optional extra (`tracking`) and is imported only when used.
- Local only. `check_tracking_uri` accepts a sqlite file, a folder or a `file:` URI and refuses http(s), databricks, database servers and object stores before anything is written. No credentials are read or stored.
- Each run records: configuration (seed, quick, bootstrap), a data fingerprint (a hash of the table and content hash of every COMPLETE ingestion batch, so it does not change with ingestion dates and ignores rejected batches), the git commit and whether the tree was dirty, library versions, the assumed cost parameters (labelled ASSUMED), about 100 metrics read from the saved JSON files under stable names, stage timings, and artifacts (reports, figures, the model bundle, small JSON files, a manifest `pipeline_run.json`). Baseline model files are not logged because they are large and reproducible.
- Nothing that identifies the machine is recorded: MLflow's default user and script path tags are overridden (`mlflow.user=local`, `mlflow.source.name=mmrisk.pipeline`), and no hostname is logged.
- A failed run is kept and marked FAILED with the stage that failed (`failed_stage`) and the error type; Ctrl+C marks it KILLED. A run is never left looking finished.
- A `--quick` run writes to `models/quick` and `docs/quick` by default so it cannot overwrite the full run's models or the committed reports; a folder given explicitly is used as given.
- Non-finite or missing metrics are skipped and counted rather than logged as numbers.
**Alternatives.** Calling MLflow directly from every stage (couples the code to one tool and makes tests need a store); a hosted tracking server (cost, credentials, not needed at one user); an orchestrator such as Airflow (rejected, one machine and five steps); separate processes per stage (re-computes features and loses the single failure point).
**Consequences.** Runs can be compared with `python -m mmrisk.pipeline compare` or `mlflow ui --backend-store-uri sqlite:///mlflow.db`. The store is a local file and is git-ignored; it is not a backup. A model registry and promotion gates are deferred to Phase 16, where a gate needs something to protect. The full run rewrites `docs/*.md` (as the separate commands do); only quick runs are isolated. Limits: the data fingerprint covers ingested source files, not the generator's code; a dirty tree is recorded but its changes are not.
