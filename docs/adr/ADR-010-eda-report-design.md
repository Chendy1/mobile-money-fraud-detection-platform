# ADR-010: EDA as a reproducible report (DuckDB over the lake, observed labels on matured data only)
**Context.** Exploration done in a notebook produces claims nobody can re-run, numbers typed by hand go stale, and the most common EDA mistakes in fraud work are label leakage (using labels or future rows a live system would not have) and treating recent, still-unlabelled transactions as clean.
**Decision.**
- EDA is a command, `python -m mmrisk.eda`, that reads the cleaned lake and writes `docs/eda-report.md` and seven figures. Every number in the text is computed in code; each figure is titled with the question it answers.
- DuckDB reads the Parquet files directly. History features (previous transaction, counts in the last 10 minutes, 1 hour and 24 hours, running average, first device, first recipient, last inbound transfer) are SQL window functions with frames that end at `1 PRECEDING`, and an ASOF join for the inbound transfer, so a row never sees itself or later rows.
- Label statistics use only *matured* transactions: older than the dispute window (45 days) before the end of the data. The recent window is analysed separately to show how much fraud is still hidden.
- The main analysis uses observed labels only. Ground truth appears in one optional, flagged audit section and is never used elsewhere. `--no-truth` removes it.
- Group fraud rates carry Wilson 95% intervals and are called higher or lower only when the interval excludes the overall rate.
- Tests recompute the window features by brute force, check that cutting off the future leaves earlier rows unchanged, and were mutation-checked.
**Alternatives.** A Jupyter notebook (interactive, but hard to test, diff and re-run, and encourages hand-typed conclusions); pandas-profiling style automatic reports (generic, no questions, no leakage handling); computing the history features in Polars (possible, but rolling windows over time and ASOF joins are clearer in SQL, and this analysis layer is a first draft of the Phase 6 feature definitions).
**Consequences.** The analysis is repeatable and reviewable; the report refreshes when data is regenerated. Costs: two extra optional dependencies (`duckdb`, `matplotlib`); the SQL here is not yet the production feature code, so Phase 6 must re-implement it as a shared library and test it against these definitions; thresholds for the behavioural signals (5x, 2 minutes, and so on) are illustrative, not tuned; findings describe the simulator and not real traffic.
